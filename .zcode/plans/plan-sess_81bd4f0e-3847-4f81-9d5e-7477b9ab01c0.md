# 明庭改造为任务中台：发布不派发 + 手动派发

## Context

明庭当前的发布语义是「发布即派发」：`publication.publish()` 落库后立刻 `store.deliver()` 生成 `task.available` 事件，SSE 推给在线执行者，执行者自动认领执行。用户要把明庭先定位为**任务中台**：只提供任务发布与任务查看，不主动派发；发布时支持不触发执行者；同时保留「选择执行者」的派发模式。

**采用语义（用户未作答，按推荐项执行）**：
- **派发与否 = 发布时是否选择执行者**。不填 `targetHarness` → 任务登记为「待派发」，不产生投递事件、不推送、不可认领；填了 `targetHarness` → 保持现有定向派发行为。
- **提供手动派发入口**：待派发任务可由网页按钮或 MCP `action:"dispatch"` 命令派发，派发时可指定/修改执行者，之后走现有投递/认领流程。原「任意执行者先到先得」的广播派发不再作为默认提供。

**隐藏坑（探索确认）**：只跳过 `deliver()` 不够——首轮任务认领不强制 deliveryId（[runs.ts:74](src/server/tasks/runs.ts#L74)），在线执行者仍可直接 claim。因此需要任务级状态挡认领。

## 语义规则

| 场景 | 行为 |
|---|---|
| 发布（new）不带 `targetHarness` | 任务 `status: "awaiting_dispatch"`（待派发），无 delivery、无推送、claim 拒绝 |
| 发布带 `targetHarness` | 现状不变：`queued` + delivery + 定向推送/认领 |
| `dispatch`（MCP 命令 / 网页按钮） | 仅限 `awaiting_dispatch` 任务；必须能解析出执行者（命令带的 `targetHarness`，否则用任务已有值，都没有则 400）；置为 `queued` + delivery + 推送 |
| dispatch 已派发/终态任务 | 409 |
| 取消 `awaiting_dispatch` 任务 | 允许（现有 cancel 白名单需补充） |
| 队列上限 | `countActive()`（[store.ts:348](src/server/storage/store.ts#L348)）不含 `awaiting_dispatch`——待派发任务不占执行队列 100 上限 |
| 追加（append）待派发任务 | 409「任务尚未派发」，给明确报错（现在会误报"原执行尚未释放"） |

## 改动清单

### 1. 协议与共享层
- [src/shared/protocol.ts:196](src/shared/protocol.ts#L196) `taskStatusSchema` 增加 `"awaiting_dispatch"`（放在 `"queued"` 前）。
- [src/shared/host-wakeup.ts](src/shared/host-wakeup.ts)：新增 `dispatchTaskSchema`（`action:"dispatch"` + `taskId` + 可选 `targetHarness`）；`taskCommandSchema` 并入 dispatch 分支；[protocol.ts:191](src/shared/protocol.ts#L191) `mcpTaskCommandSchema` 的 `action` 枚举加 `"dispatch"`；更新 `taskCommandDescription` 说明新语义（不填执行者=登记待派发；填执行者=立即派发；dispatch 手动派发）。

### 2. 存储层 [src/server/storage/store.ts](src/server/storage/store.ts)
- `publish()`（L376）：初始状态改为 `input.targetHarness ? "queued" : "awaiting_dispatch"`（saveTurn 沿用该状态）。
- `countActive()`、`deliver()`、`saveTask()`（自动同步轮次状态）无需改动。

### 3. 任务服务 [src/server/tasks/](src/server/tasks)
- `publication.ts`：
  - `publish()` L247：`event` 仅在 `input.targetHarness` 存在时调 `store.deliver()`，否则 `undefined`（幂等重放路径本就不投递，不受影响）。
  - `publishCommand()` L152：增加 `action === "dispatch"` 分支 → 新方法 `dispatch(taskId, targetHarness?)`：事务内校验任务存在（404）、状态为 `awaiting_dispatch`（否则 409「任务已派发或已结束」）、解析执行者（无则 400「派发需要指定执行者」）、写回 `targetHarness` + `status:"queued"`、`saveTask`、记 `task_communications`（type `"dispatch"`）、`store.deliver()`；事务外 `available(event)` 触发推送。
  - `append()`：对 `awaiting_dispatch` 任务给明确的 409 报错。
- `runs.ts`：
  - `claim()` L98 前增加对 `awaiting_dispatch` 的显式拦截（409「任务尚未派发」），否则现有 `!== "queued"` 检查会误报「任务已领取或已结束」。
  - `cancel()` L297 白名单加入 `"awaiting_dispatch"`。
- `retry()` 只允许终态任务，天然不受影响（ dispatched 任务 retry 沿用原执行者重新投递，行为不变）。

### 4. 传输层
- [src/server/transport/browser-api/router.ts](src/server/transport/browser-api/router.ts)：仿 retry（L110）新增 `POST /api/tasks/:id/dispatch`，body 校验 `targetHarness` 可选，走 `taskExchange` 记通信。
- [src/server/transport/mcp.ts](src/server/transport/mcp.ts)：无结构改动（dispatch 走同一 `mcp-mingting-tool` 命令联合，工具描述随 `taskCommandDescription` 自动更新）。
- SSE 推送过滤（[connector.ts:99](src/server/transport/connector.ts#L99)）无需改：派发后的任务必有 `targetHarness`，过滤逻辑不变；遗留的旧 queued 无目标任务仍广播（向后兼容）。

### 5. 网页 [src/web/main.tsx](src/web/main.tsx)
- 状态标签映射（L86）加 `awaiting_dispatch: "待派发"`。
- 任务列表/详情：`awaiting_dispatch` 任务显示「派发」按钮 → 执行者选择弹层（复用 `/api/harnesses` 在线列表 + 发布弹窗的 datalist 模式），成功后刷新；离线执行者也可选（任务保持排队，等其上线，与现状一致）。
- 发布弹窗「执行者」输入的辅助文案与流程提示（L677）更新为新语义。
- 检查 L1341 的活跃状态轮询列表是否需要纳入 `awaiting_dispatch`（预计不需要：派发操作本身会刷新）。

### 6. 脚本
- [scripts/publish-task.ts](scripts/publish-task.ts)：更新用法说明（不传第 5 参 = 登记待派发）。

## 测试

**更新现有用例**（核心工作量）：[tests/platform.test.ts](tests/platform.test.ts)、[tests/routing.test.ts](tests/routing.test.ts) 中大量「发布不带执行者却期望被执行」的用例，需给发布参数补 `targetHarness` 或改断言为待派发。

**新增用例**：
1. 发布不带执行者 → `awaiting_dispatch`，无 delivery，在线执行者收不到事件，直接 claim 被拒，任务保持待派发。
2. 发布带执行者 → 现有定向投递/认领行为回归通过。
3. dispatch（MCP 命令 + 网页 API）→ `awaiting_dispatch`→`queued`，目标执行者收到事件并执行；非目标 403；未解析出执行者 400；重复派发/终态 409。
4. 取消待派发任务 → `cancelled`。
5. 待派发任务不占队列上限（发布 100+ 条仍可继续登记）。
6. Playwright（ui.spec.ts）：待派发徽标、派发按钮流程、发布弹窗新文案。
