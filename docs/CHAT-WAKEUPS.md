# 当前聊天的事件唤醒

状态：平台事件持久化及 ACP 原会话恢复通过隔离验证。当前聊天的 ACP 加载返回 `thread_active_writer`，真实两次唤醒验收未完成。

当前验收目标是桌面应用保持运行，常驻订阅器接收明庭事件并把输入送入桌面已持有的会话。隔离测试已验证 sessionId 映射和写入权交接，桌面宿主的输入队列接入仍待完成。

投递路径为“平台持久审批/完成事件 → 已有 CodexAdapter → ACP session/load(原聊天编号) → session/prompt(事件)”。发布与审批使用现有 MCP HTTP 工具。平台绑定承担任务事件订阅，事务提交后的通知触发投递。

## W1 发布后结束回合

发起方可在发布任务时绑定当前聊天与发布回合。绑定随任务一起保存，任务发起方私密保存原有审批订阅回执，然后结束当前回合。平台负责在审批创建及运行结束时生成持久事件并调用宿主消息入口。

## W2 审批与完成分别恢复执行

每张待审请求生成一条 `approval.requested`，每个已结束运行生成一条 `task.completed`。事件保留任务、运行、目标聊天及原始事件 ID。宿主将事件送回同一聊天，发起方在新的回合处理审批、结束回合，再由完成事件恢复检查成果。

投递回执表示宿主接收了消息。接收方需确认实际恢复的回合；真实验收还需核对宿主聊天记录中前一回合已结束、事件消息与新回合对应，及两次恢复回合各自独立。

## W3 失败与回放

宿主接入不可用时，带聊天唤醒的发布请求明确失败，任务列表保持原样。投递失败持久保留，恢复后按既有记录处理；同一事件的重复状态保存沿用原事件 ID。投递状态、恢复确认与聊天记录共同构成回放证据。

当前聊天探测：2026-11-01 20:15（Asia/Shanghai），ACP 2.5.0 声明 loadSession=true，加载当前聊天返回“session is in use by another Codex client”。同项目一条已结束回合的聊天也返回占用。真实 Codex 加本地测试模型的隔离用例证实：完成回合后仍持有写入权；持有进程退出后，新 ACP 连接可以按原编号继续。此结果确认原历史恢复能力。当前桌面内唤醒的接入目标为已持有会话的宿主，桌面继续管理该聊天。

真实验收按“发布回合结束 → 审批事件恢复新回合 → 审批回合结束 → 完成事件恢复新回合 → 成果复核”判定。测试中的模拟宿主结果单独标明；原有 R1–R10 继续验证审批传输与裁决。

## 操作入口

先在当前 Codex 聊天的执行环境检查宿主能力：

```bash
npm run chat:wakeup -- probe
```

探测通过 ACP 初始化及原会话加载确认能力，随后回收探测进程；模型回合保持未启动。成功后，按现有启停流程设置 `MINGTING_CODEX_WAKEUPS=1` 与原 `CODEX_THREAD_ID`。`MINGTING_CODEX_HOME` 指向原聊天的 Codex 数据目录；`MINGTING_CODEX_WORKSPACE` 指向原聊天工作区。执行连接器保留自己的工作区和登录配置。预检确认的原聊天为本次授权范围。原客户端持有写入权时，探测保留实际错误，唤醒发布返回失败。

每次事件沿用原编号加载，首个模型输出确认投递，ACP prompt 连接保持到本轮结束后回收。完成事件等待前一 ACP 回合收尾，再加载原会话。权限请求沿用当前会话策略并按未授权处理；新增权限授权由用户指定。标准 MCP Events 可作为后续独立接入方式，当前 ACP 方案的实现与验收以本节为准。

| MCP 工具                  | 输入与结果                                                                                                |
| ------------------------- | --------------------------------------------------------------------------------------------------------- |
| `get_wakeup_status`       | `{}`，返回 `{available, transport, error}`                                                                |
| `publish_task`            | 原发布参数增加可选 `wakeup: {threadId, originTurnId}`；唤醒任务同时选择 subscriber 审批；返回原回执及绑定 |
| `get_task_wakeups`        | 原 `approvalSubscription`，返回此任务的目标与持久事件/投递状态                                            |
| `acknowledge_task_wakeup` | 订阅对象加 `{eventId, threadId, turnId}`，记录新的恢复回合；相同确认幂等                                  |

只在 `available: true` 时开始真实验收。发布参数放进 JSON 文件，回执选择项目忽略的私有目录。发布命令自动使用当前 `CODEX_THREAD_ID`：

```bash
npm run chat:wakeup -- publish <当前发布回合UUID> <发布参数JSON路径> <全新私密回执路径>
```

命令成功返回后立即结束聊天回合。平台在事务提交后直接投递 `[MINGTING_EVENT <事件ID>]` 消息，目标包含同一聊天、任务、运行和审批标识。

审批事件恢复后，发起方核对当前聊天和新回合，调用 `get_task_wakeups` 一次、确认对应事件，然后检查完整权限请求并提交原始单次选项，随即结束回合。完成事件再次恢复后，确认另一独立回合，读取结果并核对任务验收条件。订阅回执保存在发布时的私密路径；事件正文仅携带定位信息。

收到事件后的单次读取与确认也提供命令行入口：

```bash
npm run chat:wakeup -- events <私密回执路径>
npm run chat:wakeup -- ack <私密回执路径> <入站事件ID> <本次恢复回合UUID>
```

## 回放证据

原生 ACP 写入权交接的可重复用例：`npm run test:acp-session`。它使用真实 Codex/ACP、全新临时会话和本地模型夹具，结果保存在 `reports/chat-wakeups/development/acp-native-ownership.json`。该用例独立验证占用及同编号恢复；本聊天两次事件的真实验收按下面的宿主记录判定。

真实回放输入为 `src/shared/wakeup-replay.ts` 的 `wakeupReplaySchema`：包含真实模式、任务与目标、持久事件，以及实际 `read_thread` 返回的 `thread` / `turns` 记录。取证时保留来源、采集命令和文件哈希。恢复确认与回放校验分别承担“记录接收方声明”和“核对宿主记录一致性”的职责。

```bash
npm run chat:wakeup -- replay <真实回放JSON路径>
```

该命令在本机报告目录保存原输入、逐项判定和回放页面，失败返回退出码 1。探测失败返回退出码 2，并将发布、审批唤醒及完成唤醒标记为未开始。

平台事件状态依次为 pending、sending、delivered、acknowledged。失效审批为 superseded；投递失败为 failed。进程在 sending 阶段退出后，原投递结果记为待确认，核对宿主记录后再决定后续操作。队列投递由提交后的变化通知和启动恢复驱动，现有连接器的执行租约保持原有规则。
