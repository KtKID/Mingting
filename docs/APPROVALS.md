# 审批

## A1 任务发起方与审批对象

执行者在运行任务时通过 ACP `session/request_permission` 向明庭申请审批。任务发起方是本任务的审批订阅者，例如 Codex 发起任务、Grok 执行任务时，由发起方 Codex 接收审批。执行身份与审批订阅身份分别绑定。

发布任务时可以多选审批对象，默认勾选“订阅者”；“第三方”显示为置灰的“开发中”。首版支持 `approvalTargets: ["subscriber"]` 和 `[]`（由用户审批）。协议保留 `third_party`，首版服务端对包含该值的发布返回 400，并保持任务列表原样。用户始终可以审批。

`mcp-mingting-tool` 返回 `taskId` 和 `approvalSubscription: {taskId, subscriptionToken}`。任务专属凭据只返回给发起方，数据库保存凭据哈希；任务列表、网页快照、执行领取、审批通知均排除该凭据。`publisherName` 继续用于展示。

发起方保存 `approvalSubscription` 后可选择以下接收方式：

| 接口                                   | 行为                                                                                                                                                  |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| MCP `wait_for_approval`                | 输入发布返回的订阅对象，可选 `waitMs`（0–25000，默认25000）。有待审请求时立即返回；其余时间等待新请求、任务结束或本轮等待结束。任务仍活动时继续调用。 |
| HTTP `GET /subscriber/events?taskId=…` | 通过 `Authorization: Bearer <subscriptionToken>` 建立常驻 SSE，接收 `approval.snapshot`。连接建立时返回当前待审快照，之后推送变化。                   |
| MCP `submit_approval_decision`         | 输入订阅对象、`approvalId`、`runId`、`sessionId`、原始 `optionId`，提交订阅者意见。                                                                   |
| HTTP `POST /subscriber/decision`       | 使用与 `submit_approval_decision` 相同的输入。供可信本机客户端使用。                                                                                  |

接收快照包含任务状态、当前运行的待审请求、各审批方意见和截止时间。审批和意见保存在 SQLite；重新订阅会恢复当前状态。MCP 接收采用有界等待，活跃调用方负责继续等待；SSE 提供常驻推送。首版每项等待/流最多8个连接，保留原有可信本机访问边界。

## A2 弹窗、标题与描述

网页无论停留在列表或任务详情，收到新审批后自动弹窗。弹窗展示标题、描述、订阅者和用户的意见、“拒绝”“同意”。关闭弹窗后可以在对应任务详情继续审批；多张审批依次显示。详情保存两方意见与最终采用方。

ACP v1 保留原始 `toolCall` 和 `options`。执行者可在 ACP 请求的 `_meta["mingting.dev/approval"]` 附带 `title`、`description`。沿用标准字段的执行者使用 `toolCall.title` 作为标题，工具文本、原始输入或文件路径作为描述。弹窗提供原始操作上下文，保留完整请求以便判断。

“同意”“拒绝”优先映射到执行者提供的 `allow_once` / `reject_once`。执行者仅提供记忆选项时，界面展示其授权范围，再使用相应原始选项。对应选项缺失时，按钮保持禁用。

## A3 用户优先与十秒窗口

| 触发                               | 状态和结果                                                   |
| ---------------------------------- | ------------------------------------------------------------ |
| 审批创建                           | 用户与订阅者均为待决定，执行者等待。                         |
| 用户先决定                         | 立即采用用户选项，结束本次审批并回传 ACP。                   |
| 订阅者先决定                       | 保存意见，服务端从接收时起计时10秒；弹窗右上角显示剩余时间。 |
| 十秒内用户决定                     | 立即采用用户选项，保留订阅者意见供查阅。                     |
| 十秒结束、用户仍待决定             | 采用订阅者选项，结束本次审批并回传 ACP。                     |
| 重复提交相同订阅者意见             | 保留首次意见和原截止时间。变更已提交意见返回409。            |
| 审批结束后再次提交                 | 返回409，已结束审批的结果保持稳定。                          |
| 取消、运行结束、租约失效或服务重启 | 待审请求失效，历史意见保留。                                 |

截止时间由服务端保存和执行，250ms巡检及请求入口都会检查截止时间。网页用服务端时间校准显示；刷新、暂时离线和关闭弹窗沿用原截止时间。每张审批独立计时。订阅者保持待决定时，沿用10分钟审批等待上限；收到有效订阅者意见后保留完整10秒窗口。原有30分钟执行上限和连接器租约继续生效。

用户优先适用于仍在等待的审批。回传最终结果后，本次审批结束，已开始的实际操作按原执行器语义处理。

## A4 真实数据复用与网页回放

将已完成的真实 ZCode 审批录制为只读夹具，保留源任务、请求、返回和哈希。测试在日常60390平台重新发布带“审批回放”标记的任务，使用独立回放执行身份；模型与文件工具采用录制结果，平台发布、订阅、ACP 往返、持久化、网页按钮和十秒窗口沿用真实链路。四种双方意见组合、用户先决定、订阅者十秒回退、刷新及取消逐项核对。

同源 `/approval-tests/` 提供浅色 HTML 测试记录，展示用例矩阵、逐步截图、时间线和断言，并链接到任务详情。原始真实数据继续保留。[回放任务记录](task/task-approval-replay.md)记录本轮实施和结果。

## A5 默认自动回归与批次留存

任务台标题旁提供“审批回放与测试记录”。默认 `npm test` 和 `npm run check` 自动运行后端与离线 ACP 回放、构建、桌面和手机网页回归、R1–R10 浏览器审批。发布、审批回传与落库由接口测试覆盖。发布表单、审批弹窗、操作按钮、结果展示与重连由 Playwright 操作。模型和工具使用测试输入。审批专项命令复用同一运行器。

GitHub Actions 配置在 PR 和 main 更新时运行同一个 `npm test`，保留批次证据。默认批次的网页阶段缺失或失败时，整体结果为失败。[自动回归任务](task/task-automatic-regression.md)

每次运行创建独立批次，保留输入录制与源数据哈希、代码基线、逐例任务快照、判定、截图、trace、日志及退出码。成功、失败、中断和未执行分别记录，历史批次保持完整。回放页可切换批次；60391隔离回归的结果通过归档快照查看，60390既有回放任务保留直接链接。[默认回归任务](task/task-approval-default-regression.md)维护本次实现与验证。
