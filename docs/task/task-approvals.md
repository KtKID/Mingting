# 发起方订阅审批与用户优先

## ① 需求与变更

来源：2026-11-01本次用户要求及角色澄清。执行者经ACP向明庭提交带标题、描述的请求；任务发起方接收审批。例如Codex发起任务时，Codex是该任务审批订阅者。发布时多选审批对象，首版启用订阅者、第三方置灰。网页弹窗包含两方状态与同意/拒绝；订阅者先决定后倒计时10秒，窗口内用户优先，窗口结束沿用订阅者意见。

基线：`ba4968b`，工作区开始时干净。原功能正文快照见 `reports/approvals/HARNESS-SUBSCRIPTIONS.before.md`。当前主定义为 [A1–A3](../APPROVALS.md)，本次所有实现均在本项目。

## ② 设计

- D1/A1：共享Zod定义多选审批目标和审批订阅输入。发布事务生成任务专属随机凭据并持久化哈希，领取数据与网页状态沿用原数据职责。审批提供方意见按带target的数组保存，保留后续并行提供方扩展点。
- D2/A1：复用持久审批与服务变更通知。发起方通过任务专属SSE快照或MCP有界等待接收；MCP/HTTP提交意见共用裁决入口。任务发布者展示名、执行连接器所有权与审批订阅凭据分别处理。
- D3/A2：提取ACP工具标题、原始操作说明及可选命名空间元数据；React统一组件用于弹窗和历史。全局待审快照触发弹窗；关闭后可在任务详情处理。按钮绑定原始ACP选项，优先单次授权，显示持续授权范围。
- D4/A3：记录每方选项、决定时间、fallbackAt与resolvedBy；用户直接终结，订阅者仅启动10秒窗口。定时巡检与提交/查询入口共同处理截止时间，最终结果仅通过既有ACP回调返回。相同意见重试沿用原截止时间。
- D5/A3：沿用run/session/claim/currentRun隔离、取消、租约、超时和恢复机制。重启使待审请求失效；历史意见保留。浏览器按服务端时间校正剩余时间。

适用规范：使用dev-ts的共享Zod、派生类型、官方SDK协议校验与显式异步清理原则。沿用项目strict tsc、Prettier及现有测试框架；本轮依赖与lock保持原样。HTTP/MCP继续使用本机访问约束，模拟测试服务与当前部署的数据库分别运行。

## ④ 实现

协议：`src/shared/protocol.ts`、`src/shared/approval.ts`。持久化与裁决：`src/server/store.ts`、`src/server/service.ts`。入口与通知：`src/server/http.ts`。界面：`src/web/main.tsx`、`src/web/approval-card.tsx`、`src/web/style.css`。说明：本功能正文、Harness索引与中英文README。

无新增依赖。第三方审批保留协议角色和多选界面入口，首版明确禁用。常驻SSE与MCP等待都依赖已连接客户端接收，模型调用由任务发起方处理。
