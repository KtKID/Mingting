# ZCode、Grok 与 DeepSeek Harness 接入统一 ACP 审计

> 设计基线 [Codex 已确认的 ACP 统一层](../spec/codex-task-settings-and-audit/tech-design.md)

## ① 需求与变更

用户授权以 x-qdev 扩展已有 ACP 架构，并为三家各发轻量任务验证执行和审计。复用现有任务 API、租约、SQLite 和运行查询。初始基线、已有 Codex 改动与本轮差异分开记录。

## ② 精简技术设计

D1 复用已确认的 D01–D04。公共 ACP 客户端处理标准会话、配置、流、审批和序号。运行层按已注册 Harness 校验归属。执行器私有回包由各自映射模块转换。现有 Codex 入口和原会话唤醒继续使用既有适配行为。

D2 Grok 用原生 ACP，DeepSeek 用官方 `dsh --profile acp`，ZCode 沿用明庭到原生 app-server 的 ACP 桥。优先从实际选项和回读生成回执。执行器缺报的字段保持未知，目录窗口标明来源。通过安全读取任务验证，原有授权和审批边界保持适用。

D3 明庭统一计数和来源。Grok 取 prompt 元数据，ZCode 取一次原生会话的计数，DeepSeek ACP 缺报时仅核对同一新会话的完整 v4 日志。按提交步骤计数，拒绝错会话、重复、未完成和含重试的日志。各来源的模型目录和有效窗口分开保存。

## ③ 测试用例与变化

## ④ 技术实现

公共 ACP 客户端统一选项探测、提交回执、事件转发和子进程生命周期。各家私有字段由各自映射模块读取。连接器继续使用已有租约和序号，SQLite 和 Web 复用同一份运行模型。ZCode 复用 Read 限制和双向原生审批。DeepSeek 新增隔离运行目录与用量补读。

## ⑤ 验证结果

三家真实读取、正文流、模型与档位回执、上下文、工具和 Usage 对账通过。ZCode 实测 Read 审批。Grok 和 DeepSeek 的读取由上游直接执行，审批往返由受控用例覆盖。DeepSeek 的思考内容与思考 token 在本次回合缺报。正式服务启用与项目登录更新保留为部署事项。[统一测试报告](../../reports/multi-harness-acp/20261106-qdev/test-report.md)
