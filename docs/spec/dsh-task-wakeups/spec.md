# DSH 发布明庭任务后唤醒原会话

用户从 DSH Web 的任一会话发布明庭任务。明庭记住发起任务的会话和轮次，任务完成后让同一个会话自动开始新一轮。

## 本次目标与完成条件

- **目标与范围**　支持同一个 DSH Web 上的现有「孔明」会话和普通新会话。发布时自动关联当前会话和当前轮次，任务完成时自动回到发起会话。支持由用户在明庭网页处理任务审批。
- **验证证据**　从两个真实会话各发一条测试任务，记录发布顺序、任务编号、各自的发起轮次、完成顺序、通知归属和新轮次。两条任务发布后结束各自发起轮次，等待完成通知自动触发后续轮次。
- **完成条件**　先发的任务后完成。每次完成后，只在对应的发布会话内看到该任务的完成通知和一个新轮次。原「孔明」会话沿用其聊天记录。新开的 DSH Web 会话只用于第二条任务的发布和接收。
- **确认依据**　用户确认按发布方身份绑定、原会话接收和审批独立的方案实施，并明确指定上述两个会话和交错完成验收。

## feat01: 发布时自动关联当前会话

在 DSH Web 里发布明庭任务时，任务带上实际发起会话及轮次。

**场景1　两个会话各自发布**

必要性　用户要求现有「孔明」和新会话分别真实发布。核对两条任务的发起信息才能排除沿用固定接收会话。

- GIVEN 「孔明」原会话和一个新建 DSH Web 会话均可发布明庭任务
- WHEN 用户在两个会话中各自委托发布一条测试任务
- THEN 两个会话分别收到自己的任务编号，明庭记录与实际发起的会话和轮次一致，发布时无需手填接收会话

**场景2　无法确认发起会话**

必要性　每次发布须关联实际发起会话，且既有唤醒约定要求接收方不可用时明确告知。来源无法确认时照常发布会让用户误以为任务结束后会自动回来。

- GIVEN 明庭无法确认这次发布来自哪个可接收完成通知的会话
- WHEN 用户尝试从当前会话发布带完成唤醒的任务
- THEN 发布明确失败并说明原因，明庭任务列表保持原样，其他会话保持原有状态

## feat02: 任务完成后回到原会话

任务完成后，发起它的会话收到对应的完成通知并自动开始新一轮。

**场景1　先发后完成，逐条核对归属**

必要性　用户要求两条任务交错完成。逆序完成能检验通知归属与发布顺序和当前显示的会话相互独立。

- GIVEN 「孔明」先发布任务 A 并结束发起轮次，随后新会话发布任务 B 并结束发起轮次，两个会话均选择由用户在明庭网页审批
- WHEN 任务 B 先完成，此时任务 A 仍未完成，随后任务 A 完成
- THEN B 完成后只有新会话收到 B 的通知并开启一轮。A 完成后只有原「孔明」会话收到 A 的通知并开启一轮。每条通知与对应任务编号一致，两个新轮次都在各自原会话里

**场景2　同一完成通知重复送达**

必要性　用户认可按事件去重。同一通知重复到达时，额外开启轮次会破坏一条任务对应一次唤醒的验收判据。

- GIVEN 发起会话已收到任务的完成通知并开始新一轮
- WHEN 同一条完成通知再次送达
- THEN 原会话中该通知只出现一次，对应的新轮次只有一个

**场景3　任务需要网页审批**

必要性　已确认网页审批与完成唤醒可以同时使用。验证实际有审批的任务能区分审批过程和任务完成。

- GIVEN 用户从 DSH Web 发布任务并选择由用户在明庭网页审批，该任务发出一项权限请求
- WHEN 用户在明庭网页作出审批决定，任务随后完成
- THEN 网页保留该项审批的决定，任务完成后发起会话收到对应的完成通知并开始新一轮
