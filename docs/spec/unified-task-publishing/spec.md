# 统一发布明庭任务和订阅结果

客户端统一通过 MCP 发布明庭任务，明庭任务网页保留发单能力。两种入口接受同一套任务内容，给出同一种发布回执。订阅者凭回执接收结果，执行者领取并完成任务，被唤醒者由已注册的 Harness 和该 Harness 下的会话 ID 确定。会话内发单时，默认把完成通知送回实际发单会话。明确配置目标时，通知送到指定的已有会话。

## 本次目标与完成条件

- **本次目标与范围**　将旧客户端专属发单替换为通用 MCP 发单。MCP 和网页共用同一个发布动作、同一份任务内容和同一种回执。网页发单时没有聊天唤醒目标。任务结果订阅与审批方式独立。
- **验证证据**　从 KMH 60000 网页打开已有的「孔明」会话和普通会话，分别真实发单并在各自原聊天记录验证完成通知。另用网页默认生成的会话身份覆盖默认行为。明庭任务网页发单另测。涉及创建文件的任务检查指定文件实际存在。
- **交付顺序**　第一阶段先跑通 KMH 内任一用户会话的统一发布、结果订阅和唤醒。显式目标可选择同一已注册 KMH 实例中的已有会话。验收期间保留旧入口与已有任务，已有任务按原流程继续执行、接收通知和查询。第二阶段在第一阶段验证通过并确认切换后，才退役旧专属入口的新发单能力。已有任务与历史记录继续可用。
- **完成条件**　第一阶段要求统一入口的任务能拿到可用回执，网页发单可照常审批、执行和查看结果，已登记唤醒目标的任务只在对应原会话开启一次新轮次，断线或晚订阅能补收结果。旧专属入口停止接收新任务是第二阶段的完成条件。
- **关联范围**　[原专属发单方案](../dsh-task-wakeups/tech-design.md)由本需求替代。[原会话唤醒需求](../dsh-task-wakeups/spec.md)中的原会话归属、事件去重和网页审批可与完成唤醒并用的验收要求继续适用。

## feat01: 用统一规则发布任务并取得回执

用户可以在任一已接入的客户端会话或明庭任务网页发单，取得任务编号、链接和独立的结果订阅回执。MCP 发单工具名为 `mcp-mingting-tool`。KMH 的孔明和普通会话由同一个插件发单，插件自动使用实际会话身份。

**场景1　用已有会话发单并登记本会话**

KMH 网页的用户会话统一支持发单和接收唤醒。60000 验收在已有的「孔明」和普通会话各发两笔任务，网页选择 zai-coding-cn 的 GLM-5.3，核对四个单行文件和四次各自独立的自动续轮。

- GIVEN 会话 A 和 B 都已接入明庭，均沿用默认唤醒目标
- WHEN 用户在已有会话 A 发一条任务，再在会话 B 发另一条
- THEN 两次发单返回同一种格式的回执。两条任务分别登记实际的 A 和 B，用户只需填写任务和执行要求

**场景2　从明庭任务网页发单**

用户确认网页发单与其他发单只在聊天唤醒目标上有差别。需要核对网页任务的回执、执行和结果依然完整。

- GIVEN 用户打开明庭任务网页
- WHEN 用户提交任务、查看回执并等待任务结束
- THEN 明庭按统一规则创建任务并给出同一种回执，任务可以照常审批、执行和查看结果。详情显示无聊天唤醒目标，任务结束时没有聊天被自动唤醒

**场景3　退役旧专属发单**

用户要求退役旧专属发单方式。需要检查旧方式已停止创建新任务，避免两套发单方式继续并存。

- GIVEN 第一阶段统一发布已验收通过，用户确认切换到统一入口
- WHEN 用户尝试沿用原先的专属发单方式
- THEN 旧方式无法创建任务，用户可通过 MCP 发布。此前的任务及其已有记录可照常查看

**场景4　无法确认唤醒目标**

此前的实际故障曾返回成功回执却没有登记目标。原有验收要求这类请求明确失败，避免用户一直等通知。

- GIVEN 无法确认实际发单会话，或者配置指定的 Harness 或会话无法验证
- WHEN 用户通过 MCP 发单
- THEN 发单失败并告知原因，任务列表没有新增该任务

**场景5　唤醒配置指定的已有会话**

用户确认被唤醒者可以按已注册的 Harness 和会话 ID 指定。需要分别核对结果订阅和会话唤醒的归属。

- GIVEN 会话 A 是发单会话，用户已将同一已注册 KMH 实例中的已有会话 B 配置为被唤醒者
- WHEN 用户在 A 通过 MCP 发单，执行者随后完成任务
- THEN 回执和任务详情对应配置中的目标 Harness 与 B。订阅者收到执行结果，完成通知只在 B 的原会话历史中出现一次，A 未因该通知被唤醒

## feat02: 订阅任务结果

发布方取得回执后可订阅任务结果。结果包含实际运行状态、输出及错误，晚订阅和重连可补收。KMH 的目标会话收到完成通知和结果摘要，并继续处理。明庭任务详情显示发单时保存的唤醒会话和发单轮次，以及实际投递状态。

**场景1　发布结束后收到执行结果**

用户要求拿到回执就结束发单轮次，等执行者完成后由订阅路径通知。这个场景独立核对回执、实际交付和结果。

- GIVEN 发布方通过 MCP 发单，只要求订阅结果，取得回执后已结束发单轮次。订阅者正在等待对应任务的结果
- WHEN 执行者完成任务
- THEN 订阅者收到带对应任务编号的实际结束状态和结果，明庭任务详情可查到同一结果

**场景2　网页审批后仍收到结果**

已确认网页用户可以处理审批，同时保留结果通知。需要用实际触发审批的任务验证两件事都能完成。

- GIVEN 一笔已登记唤醒目标且只由网页用户审批的任务发出了审批请求
- WHEN 用户在明庭网页裁决，执行者继续并结束任务
- THEN 任务详情保留审批决定，订阅者收到执行结果，原会话收到对应完成通知并开启一次新轮次

**场景3　晚订阅或断线后补收**

发单与执行独立推进，执行者可能先结束。需要验证订阅者能用回执取回对应结果。

- GIVEN 发布方持有回执，任务结束时订阅者尚未连接或暂时断线
- WHEN 订阅者开始或恢复订阅
- THEN 订阅者能补收到这笔任务的结果，任务详情与通知内容一致

**场景4　两条任务各自回到原会话**

原有验收要求交错完成和重复送达时仍准确区分目标。需要核对任务归属和新轮次数量。

- GIVEN 会话 A 和 B 各有一笔采用默认唤醒目标的任务，两次发单轮次都已结束
- WHEN 后发任务先结束，先发任务随后结束，其中一条完成通知再次送达
- THEN 两条任务各自只在原有的 A 或 B 会话收到一次对应完成通知并继续处理，沿用各自的会话标识和聊天记录。其他会话收到零次，任务完成后新增的会话数为零
